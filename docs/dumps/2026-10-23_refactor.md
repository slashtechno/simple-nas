# Refactor log, 2026-10-23: drive roles, opt-in services, root drive

Resume point if the session dies. Branch: `roles-and-opt-in`, off `main` at `4534467`. Transient; nothing else cites it.

## Owner brief (verbatim)

- Docs answer the important questions and make the rest easy to find. No "used to be" or "now" wording. A beginner can adapt the repo without an AI agent.
- Drives and roles: adapt to situations; moving data (Immich to the slow drive) must be easy; two drives must be no worse than three; a root drive plus a USB backup drive, or a root drive plus a cloud-only backup, must work; the root drive is not always a microSD (NVMe and USB boot are common).
- Opt-in: today only Garage and Crafty are opt-in. Consider making every service opt-in instead of separate NAS and general-server roles.
- General hosts are not second-class: a Pi 4 on a USB backup drive running services from the microSD, or on two USB drives.
- Follow `maintaining-codebases`; beat the status quo, refactor retroactively. Put common mistakes in AGENTS.md, briefly.

## Survey baseline

- `just check` green at the start. 279 commits. Two plays in `site.yml` (hosts `nas`, `servers_general`); the NAS roles default on, the general ones default on for Dockge only.
- Behaviour keyed on group names: `site.yml` plays, `teardown.yml` plays, `roles/storage` asserts (NAS needs all three roles, general needs `fast`), `'nas' in group_names` in three backup templates, `tests/inventory.yml`, `tests/render.yml`.
- `derived.yml` gives `""` for an unclaimed role. A service path built from it then points at the root of the filesystem.
- The backup role needs a `backup` role on a `uuid` drive. Every backup script guards with `mountpoint -q <backup_drive>`.
- Docs say "microSD" where they mean the root drive.

## Decisions

| ID | Decision | Why |
|---|---|---|
| D1 | One play over `servers` in `site.yml` and in `teardown.yml`. Every role is gated by `<name>_enabled`. | A role runs where it is switched on; no group needs to mean "NAS". |
| D2 | All `<name>_enabled` defaults live in `group_vars/all/vars.yml(.example)`, all `false`. No `default(...)` in `site.yml`. | One source per default. Role defaults are not loaded by `teardown.yml` or by the templates of other roles. |
| D3 | `nas` stays as an ordinary inventory group whose `group_vars/nas` turns the NAS services on. `servers_general` is dropped from docs and examples. | Groups share settings; they carry no behaviour. Ansible's own mechanism, nothing to learn. |
| D4 | Service settings with no host-specific meaning (data dirs, Gitea/pics/Copyparty settings) move to `group_vars/all`. `group_vars/nas` keeps the enable flags, tunnel name and ingress, backup flags. | Any host can enable any service and gets the same placeholders. |
| D5 | Data dirs stay as variables in one block of `group_vars/all/vars.yml`. Moving a service is overriding its variable. | One place to look, and the way Ansible expects overrides. |
| D6 | `drive_mounts` holds only claimed roles. `fast_drive`, `primary_drive`, `backup_drive` use `mandatory('...')`. Code that asks "is it claimed?" reads `drive_mounts`. | A host is never forced to claim a role it does not use; one that needs an unclaimed role fails with a message that names the role; nothing writes to `/`. |
| D7 | The storage role's group-keyed asserts are removed. | D6 replaces them. |
| D8 | Docs and messages say "root drive". A `drives` entry without `uuid` is a folder on the root drive. | The root drive can be a microSD, NVMe or USB drive. |
| D9 | Cloud-only backup: no `backup` role, `backup_cloud_enabled` and a repository. No local repo, local backup job or local `restic check`; dumps and logs go under `nas_base_dir`; the weekly cloud job also backs up `restic_local_paths`. Its own commit. | Owner's case (d). The cloud integrity check stays manual. |
| D10 | `teardown.yml` requires `--limit` or `--tags`. | One play over every host would otherwise tear down all of them. |
| D11 | Names on deployed hosts stay: `/opt/nas`, `nas-services`, `nas-backup-*` cron names, `nas-drive-remount`, udev file names. Only Ansible variables may be renamed. | Teardown and cleanup find deployed things by name. |
| D12 | Each owner scenario is a render-test fixture. The test also asserts that an unclaimed role fails with the message. | "Adapts" is tested, not claimed. |
| D13 | The effective `*_enabled` values for `pi4` and `pi5` are compared between `main` and the branch from a copy of the repo without the vault files. | `--list-tasks` ignores `when:` and cannot prove the owner's hosts are unchanged. |
| D14 | Per-role `tasks/teardown.yml` is not adopted. | `teardown.yml` stays the one list of what gets removed; fewer moving parts. |
