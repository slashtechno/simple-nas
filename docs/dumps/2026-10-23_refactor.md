# Refactor log, 2026-10-23: drive roles, opt-in services, root drive

Resume point if the session dies. Branch: `roles-and-opt-in`, off `main` at `4534467`. Transient; nothing else cites it.

## Owner brief (verbatim)

- Docs answer the important questions and make the rest easy to find. No "used to be" or "now" wording. A beginner can adapt the repo without an AI agent.
- Drives and roles: adapt to situations; moving data (Immich to the slow drive) must be easy; two drives must be no worse than three; a root drive plus a USB backup drive, or a root drive plus a cloud-only backup, must work; the root drive is not always a microSD (NVMe and USB boot are common).
- Opt-in: today only Garage and Crafty are opt-in. Consider making every service opt-in instead of separate NAS and general-server roles.
- General hosts are not second-class: a Pi 4 on a USB backup drive running services from the microSD, or on two USB drives.
- Follow `maintaining-codebases`; beat the status quo, refactor retroactively. Put common mistakes in AGENTS.md, briefly.

## Decisions

| ID | Decision | Why |
|---|---|---|
| D1 | One play over `servers` in `site.yml` and in `teardown.yml`. Every role is gated by `<name>_enabled`. | A role runs where it is switched on; no group needs to mean "NAS". |
| D2 | All `<name>_enabled` defaults live in `group_vars/all/vars.yml(.example)`, all `false`. No `default(...)` in `site.yml`. | One source per default. Role defaults are not loaded by `teardown.yml` or by the templates of other roles. |
| D3 | `nas` stays as an ordinary inventory group whose `group_vars/nas` turns the NAS services on. `servers_general` is dropped from docs and examples. | Groups share settings; they carry no behaviour. Ansible's own mechanism, nothing to learn. |
| D4 | Service settings with no host-specific meaning (data dirs, Gitea/pics/Copyparty settings) move to `group_vars/all`. `group_vars/nas` keeps the enable flags, tunnel name and ingress, backup flags. | Any host can enable any service and gets the same placeholders. |
| D5 | Data dirs stay as variables in one block of `group_vars/all/vars.yml`. Moving a service is overriding its variable. | One place to look, and the way Ansible expects overrides. |
| D6 | `drive_mounts` holds only claimed roles. `fast_drive`, `primary_drive`, `backup_drive` use `mandatory('...')`. Code that asks "is it claimed?" reads `drive_mounts`. | A host is never forced to claim a role it does not use; one that needs an unclaimed role fails with a message that names the role; nothing writes to `/`. |
| D7 | The storage role's group-keyed asserts are removed. | D6 replaces them. |
| D8 | Docs and messages say "root drive". A `drives` entry without `uuid` is a folder on the root drive. | The root drive can be a microSD, NVMe or USB drive. |
| D9 | Cloud-only backup: no `backup` role, `backup_cloud_enabled` and a repository. No local repo, local backup job or local `restic check`; dumps and logs go under `nas_base_dir`; the weekly cloud job also backs up `restic_local_paths`. Its own commit. | Owner's case (d). The cloud integrity check stays manual. |
| D10 | `teardown.yml` requires `--limit` or `--tags`. | One play over every host would otherwise tear down all of them. |
| D11 | Names on deployed hosts stay: `/opt/nas`, `nas-services`, `nas-backup-*` cron names, `nas-drive-remount`, udev file names. Only Ansible variables may be renamed. | Teardown and cleanup find deployed things by name. |
| D12 | Each owner scenario is a render-test fixture. The test also asserts that an unclaimed role fails with the message. | "Adapts" is tested, not claimed. |
| D13 | The effective `*_enabled` values for `pi4` and `pi5` are compared between `main` and the branch from a copy of the repo without the vault files. | `--list-tasks` ignores `when:` and cannot prove the owner's hosts are unchanged. |
| D14 | Per-role `tasks/teardown.yml` is not adopted. | `teardown.yml` stays the one list of what gets removed; fewer moving parts. |

### Service roles (adopted unless marked)

- Data dirs built from an unclaimed role land at `/` (fixed by D6).

### Storage and backup

Requirement classes:

- REQUIRED, only when the service is enabled: every `*_data_dir`/`*_location` (primary for Immich uploads and Copyparty files/collab, fast for the rest), `restic_repo_path` (backup), local backup scripts (backup).
- OPTIONAL, read `drive_mounts`: `restic_local_paths` (primary, fast, order kept so snapshot groups hold), `restic_cache_dir`, `copyparty_fast_enabled`, the Docker `{{ fast_drive }}/docker` directory, the storage uuid assert.

Findings:

- Backup templates test `'nas' in group_names`; they must test per-service flags instead (Copyparty config, Gitea, Immich dirs).
- `backup_cloud_enabled | default(false)` is repeated and undeclared in `all`; declare `backup_cloud_enabled` and `backup_local_enabled` there.
- Cloud-only needs: the local repo, init, cron, check, exclude list and scripts conditional on a local backup; mount guards only when `backup` is claimed; dumps and logs default to a root-drive directory when `backup` is unclaimed; backup-status needs a local backup.
- Reviewer proposed `/var/lib/nas-backup/...` for dumps and logs on cloud-only hosts. D9 says under `nas_base_dir`; the reviewer notes `backup-paths.txt` backs up `nas_base_dir`, so dumps would upload twice. Resolution: use `/var/lib/nas-backup`, outside `nas_base_dir`. Supersedes D9's "under `nas_base_dir`".
- A cloud-only host's cloud backup holds only config today; with no local repo it must also back up `restic_local_paths`. Owner decision to flag: Drive quota.
- Hazard: `--tags backup` skips the storage role, so with the backup drive absent the tasks create the repo on the empty mountpoint on the root drive. Add a `mountpoint -q` assert at the top of the backup role when `backup` is claimed.
- Hazard: one drive holding `backup` plus `fast` or `primary` passes today. Warn (not fail) when the backup mount equals a data mount and there is no cloud repository.
- Hazard: a service moved to a path outside any claimed mount silently leaves the daily backup. Assert in the backup role that each enabled service's data dir starts with an entry of `restic_local_paths`.
- Hazard: the cloud job exits when the backup drive is missing even though it does not need it; accepted and documented, since the dumps live there.
- Hazard: the uuid-less backup check runs only with the storage role; move it into the backup role.
- Smaller: single-role restic variables belong in `roles/backup/defaults/main.yml`; wordy or historical comments in the backup scripts; `restore-services.sh` swallows errors and has echo-only dead code; the storage role's fail message should print `drives`, not the resolved map; the rclone Google Drive tasks should only run for `rclone:` repositories.
- Wording that assumes a microSD: storage tasks, `vars.yml(.example)` comments, `common` role comment, `docs/storage.md`, `README.md`, the render test, "spinning backup drive" and "USB connection" in scripts and `app.py`, `vcgencmd` in `backups.md`.
- Wrong command: `docs/plans/drive-migration.md` `restic copy` lacks `--from-repo`.
- Refuted: the cache dir does not write to the root drive of a cloud-only host (falls back to `~/.cache/restic`); `restic_local_paths` is not empty on a root-only host (home fallback); duplicate and unknown role claims are already asserted.
- Not adopted: renaming `*_drive` variables to `*_mount` (many files, no behaviour gain); renaming deployed `nas` identifiers (D11).

### Platform roles, plays, tests

- One play: `import_role` entries with `tags` and `when: <name>_enabled | bool`; `meta: flush_handlers` after the base roles so Docker restarts before services start; backup after services (its templates read service variables); each role listed once (backup and cloudflared were listed twice with opposite defaults).
- Handlers: with one play, a `docker_data_root` change would restart Docker after containers exist; flush after storage, common, tailscale, network.
- Teardown: `rmdir nas_base_dir` runs before the backup play removes `scripts/`, so a full teardown leaves `/opt/nas`; put it last. `remove_data` is declared twice. Wipe a service's data only if its compose file exists (`stat`), so a host that never ran the service is untouched. Stale comments ("only removed when ALL services are gone", wrong role for `copyparty-funnel.sh`).
- Tests: the render test and inventory are keyed on `render-nas` and `render-general`; replace with one host per layout under `servers`; split storage validation into `tasks/validate.yml` so the test can import it without side effects; assert every `*_enabled` used in `site.yml` exists in `vars.yml.example`; shellcheck glob should use `find`.
- Fixtures: root-only plus cloud; folder plus USB backup (NVMe root); two USB; NAS two-drive; NAS three-drive; missing `fast` with Dockge on (fails naming `fast`); duplicate role; unknown role.
- Network: cloud-init network config is disabled on every host that has the directory (lockout risk on VMs); gate behind `network_disable_cloud_init: false`. `"Wired connection 1"` is hard-coded in three places; make it a setting. The direct-link revert is copied in the role and in teardown. The Docker network belongs with `compose_service`, not the Pi-only direct-link role.
- Common: zellij, Ghostty terminfo and restic/rclone install on every host; make the first two opt-in and move restic/rclone into the backup role. The zellij assert hard-fails on other architectures.
- `tailscale_funnel` fails on a host not yet joined to the tailnet; run only when Copyparty is enabled and tolerate a missing tailnet.
- `cloudflared` compares against every host's ingress via `groups['servers']`; restrict to hosts with it enabled. Historical "previous setup" comments and cleanup tasks in `cloudflared` and `tailscale` should go.
- USB automount skip list lacks `/boot/efi`. `/opt/nas` creation sits in `storage`, so `storage_enabled: false` skips it; move to `common`.
- `inventory/hosts.yml.example` uses an invalid IP; `become` is set in both `ansible.cfg` and every play.
- Rejected: renaming `nas_*` identifiers (D11); `include_tasks` in `check_keys.yml` (needs a loop); the duplicate cloudflared directory task (token is written before `compose_service`).
- Deferred, not done in this refactor: role rename `backup-status` to `backup_status` (touches the directory, `site.yml`, `teardown.yml`, docs); merging the `cf_*` and `cloudflared_*` prefixes.
