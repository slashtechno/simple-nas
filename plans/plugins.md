# Plugins

Status: decided, not built; waits for the owner's go-ahead. Two independent models ran Ansible experiments on three rounds of this plan; their disagreements were settled by tests or marked unverified. Built in one sitting, in the order under "Order of work", on one branch with small labeled commits (each leaves `just check` green), merged when the owner says.

Goal: a homelabber with basic programming and little Ansible experience can write and add a service without an AI agent and without editing core files. The core names no service that is not a core part.

## Design

- A plugin is a folder shaped like a core role plus two files: `service.yml` (its entry in the services list) and `defaults.yml` (the settings the core or other hosts read: flag, port, subdomain, data dirs, image version). Settings only the role reads stay in `defaults/main.yml`. This is the AGENTS.md rule, one sentence to teach. Folder name = role name = service key.
- `ansible/plugins/<key>/` holds a plugin you write and keep in this repo, or develop there before moving it to its own repo; it is tracked, so `just check` covers it. Crafty lives there: a bundled plugin, with no Crafty name left in the core, and a fork drops it by deleting the folder. Fetched plugins go to `ansible/plugins/.fetched/<key>/`, gitignored. pics is built as a plugin folder here and the owner then moves it to its own repo (last section). The template for authors is `ansible/plugin-template/`, not scanned, and also the test fixture: one copy (the render test reads its files by path and appends its entry to `plugin_services`, so it needs no `roles_path`).
- `just plugins` writes `group_vars/all/plugins.yml` (gitignored, never edited): `plugin_services` (entries sorted by key, so Caddy and Homepage order never flips and containers are not recreated for nothing) plus every plugin's `defaults.yml`. It builds the file in memory and writes it once, after every fetch and check has passed. Group vars are the only place visible through `hostvars` for every host, readable by `teardown.yml`, resolvable by `query('ansible.builtin.vars')` in backup, and below `host_vars` and `vars.yml`, so every owner override keeps working. Entries in a vars file are templated like `services.yml`, so Jinja in them works (tested: `to_nice_yaml` keeps `{{ }}` literal; use a `|` block with `indent`, a `>-` block produced invalid YAML). Rejected, with tests: `include_vars` in a first play (it outranks `host_vars`, so no host could override a plugin's port) and defaults carried in `service.yml` with a fallback in each reader (five-plus readers, a second place for defaults).
- A plugin is switched on per host with `<key>_enabled`, like any part. The flag is declared once, in the plugin's `defaults.yml` (default false), so it reaches every host through `plugins.yml` and no `default=''` is added to the core's lookups: a plugin that forgets its flag fails loudly in `just plugins`, not silently at deploy. It is the one flag not in `defaults-flags.yml`.
- Plugin image versions sit in the plugin's `defaults.yml`, so `vars.yml` can override them, unlike core versions (`versions.yml` wins). `tools/check_platforms.py` does not see them. The `versions.yml` comment says so.
- Tested on ansible-core 2.21; templated `apply` tags are version-sensitive, so the README states the minimum version.

## Order of work

1. Core: the sections "Core: no service is named" (`login`, `core_services`, dump scripts, alerts, `compose_service` path, the `plugins` default). Behaviour unchanged.
2. Mechanism: "Plugins in a folder" and "Plugins from git" together (generator, `roles_path`, the `site.yml` loop, tags, checks, CI and test support, the generic git clone role, the template, `docs/writing-a-plugin.md`). The first real plugin proves it, so the next step follows at once.
3. Crafty into `plugins/crafty/`, then pics into `plugins/pics/`, each with its core lines removed in the same commit ("Crafty and pics move").
4. Docs sweep and `just check`, `just _links`, `wc -w docs/*.md` before and after.
5. The owner's one-time host steps (pics to its own repo, the token rename, the first `just plugins` on each host) go in `plans/plugins-migration.md`, written at the end of the sitting; that is the only part that waits on the owner's hosts and vault.

## Core: no service is named

Behaviour unchanged.

- `services.yml` holds the built-in entries as `core_services`; `derived.yml` defines `services` as `core_services + plugin_services | default([])`. Every reader keeps its name, so a new reader cannot forget plugins. Render-test checks about core invariants loop `core_services`: the `import_role` in `site.yml`, the `docs/services.md` row, defaults parity, the Tinyauth client-id lines (`tests/render.yml:471-482`), and the compose-directory grep over `roles/` (`:456-467`).
- Login: one field, `login`, replaces `own_login` and the planned `oidc_users`. Absent: Tinyauth's gate is in front of the Caddy name (the default). `own`: the service has its own login and the gate stays off (ntfy, Copyparty, Tinyauth itself). `tinyauth`: its own login plus sign-in through Tinyauth (OIDC); the app's own accounts decide who enters (Gitea, Immich). `tinyauth_users`: sign-in through Tinyauth where the app itself lets in only the users in `service_users.<key>` (pics). Tinyauth cannot limit an OIDC client, so the core hands the list over and the plugin's role must pass it to the app, as `roles/pics/templates/pics.env.j2:18` does. Every value but absent leaves the gate off. `oidc` (the redirect URIs) and `oidc_secret` stay as data fields, required exactly with the two `tinyauth` values and checked by one assert. The gate list stays `web_services` without `login` and without a fixed `port` (a `port` has no Caddy name, so no gate); the list `service_users` may name is that plus every entry with `login: tinyauth_users`, unconditionally, replacing the hard-coded `+ ['pics']` in `roles/tinyauth/tasks/main.yml:35,51` (not filtered by `<key>_sso_enabled` like `oidc_service_keys`: with `pics_sso_enabled` off during a Tinyauth outage, a still-set `service_users.pics` must not stop the deploy, `host_vars/pinas/vars.yml:38-40`); the `TINYAUTH_APPS_*` rules stay on the gate list; `oidc_service_keys` (`derived.yml:140`) reads `login`. A core assert replaces pics's own (`roles/pics/tasks/main.yml:15-22`): with `<key>_sso_enabled` and `login: tinyauth_users`, `service_users.<key>` must be non-empty. It lives in the OIDC pre-task of `site.yml:59-75`, with the check that `oidc` and `oidc_secret` appear exactly with the two `tinyauth` values, so every deploy covers core and plugins (the generator only gives an early message). A gate plus an OIDC client on one app is therefore not expressible (`tinyauth` is the substitute), and Copyparty's conditional gate and its `idp-h-key` header (`roles/caddy/tasks/web_sites.yml:23`) stay core-only. One-time migration of the six existing entries, no alias for `own_login`; the references to update are `derived.yml:120-125`, `services.yml`'s header and entries, `defaults-flags.yml:57`, `docs/services.md:281`, `docs/caddy-reference.md:69`, the per-service table in `docs/auth-reference.md:164-168` (restated by `login` value), and `AGENTS.md:10` (services live in `core_services`; plugins add entries). (`roles/dockge/tasks/own_login.yml` is an unrelated file name.)
- Dump scripts: `roles/backup/tasks/checks.yml:92-107` looks for `<key>.sh` while `teardown_service.yml:22` removes `<compose>.sh`; they agree only because every `dump_required` entry has `key == compose`. The backup check loops the entries and stats `<compose>.sh` (its only reader is that check; `dump_service_keys` stays for the render test), so no rule is left for plugin authors; `services.yml`'s comments state the filename.
- Alerts: `alert_targets` (`derived.yml:176-186`) keeps the script senders (`system`, `unlock`) and core `scrutiny`, and adds every entry with `alert_to: true`. The sender is the service key; its setting is `<key>_alert_to`, a name in `ntfy_destinations`, default `""` in the plugin's `defaults.yml`. A new service that alerts adds one field, not a line in the core.
- `roles/compose_service` renders from the calling role's folder (`ansible_parent_role_paths | first`; tested: `role_path` is the callee's inside an imported role) instead of `{{ playbook_dir }}/roles/<name>`.
- `plugins: []` gets a documented default in `defaults.yml`.

## Plugins in a folder

- `ansible.cfg` roles_path gains `plugins` and `plugins/.fetched`; `.gitignore` gains `ansible/plugins/.fetched/` and `ansible/group_vars/all/plugins.yml`.
- `tools/plugins.yml` (a playbook; `just plugins` runs it with `--vault-password-file .vault-pass`) scans both folders and writes `plugins.yml`. It runs on `hosts: localhost`, which sees `group_vars/all` (tested against the repo's inventory), with `become: false` because `ansible.cfg` sets `become = True` and sudo would ask for a password. `deploy`, `preview` and `teardown` depend on it; `_tags` runs after it and accepts the keys in `plugin_services` (read from `plugins.yml`) and the literal tag `plugins`, since `--list-tags` shows only `always` for a looped include (tested). `just teardown` calls `_tags` inside its recipe body, so the fetch goes before that call. `just check` does not run it: CI has no cache or vault.
- `site.yml` gets one loop after `garage` and before `backup` (which checks dump scripts exist), so a plugin can rely on everything deployed before it. A fourth marked `include_*` exception, because `import_role` cannot loop (tested):

```yaml
- name: Deploy the plugins
  ansible.builtin.include_role:
    name: "{{ item.key }}"
    apply:
      tags: ["{{ item.key }}", plugins]
  loop: "{{ plugin_services | default([]) }}"
  when: lookup('ansible.builtin.vars', item.key ~ '_enabled') | bool
  tags: [always]
```

  Tested: `--tags <key>` runs one plugin (handlers included), `--tags plugins` all, `--skip-tags plugins` none (a core-only deploy; an example for "Pick what you use"). Without `tags: [always]` on the loop the include is never entered; without `apply` every inner task is filtered out and the deploy silently does nothing. `--list-tasks` shows one merged line.
- One check block in `tools/plugins.yml`, each failure naming the plugin and the field: `key` is `^[a-z][a-z0-9_]*$` and unique among core and plugin keys, counting both `plugins/` and `plugins/.fetched/` (a local copy would silently shadow the fetched one; the message gives the override path: drop the `plugins:` entry and keep `plugins/<key>/`); `<key>_enabled` is in `defaults.yml`; `<key>_port` and `<key>_subdomain` for a web service without a fixed port; `<key>_sso_enabled` with `oidc`; every name in `data`/`keep`/`no_backup` is in `defaults.yml`; no key in `defaults.yml` is already set by the core's `defaults*.yml`, `derived.yml`, `versions.yml` or another plugin (a plugin's file sorts after them and would silently win; `check_vars.py` cannot see the generated file); `tasks/main.yml` exists; `<key>_enabled` defaults to false; `<key>_alert_to` is in `defaults.yml` with `alert_to`. The generator also runs `tests/check_keys.yml` over the owner's `vars.yml` files with the known keys of the core and every plugin's `defaults.yml` and `defaults/main.yml`, so a setting renamed in a new version fails at `just plugins` instead of being ignored (CI has no fetched plugins and keeps the prefix rule).
- Backup coverage of plugin `data`/`keep` is automatic (`backup_service_dirs`); a data dir outside the drives fails the deploy while `backup_local_enabled` is on (`check_coverage.yml`), and the docs say so.
- Integrations beyond `login`, `oidc`, `alert_to` and the backup fields are done by hand, as for a built-in service: Copyparty folders and Cloudflare ingress. A plugin that needs Copyparty folders (pics) says so in its README and asserts they exist, as the pics role does now. A `dump_required` plugin installs `<service_dump_scripts_dir>/<compose>.sh` (`teardown_service.yml:20-23`, `roles/backup/tasks/checks.yml`); `services.yml`'s comments say the filename rule.
- Keeping `just check` green without the generated file: `tools/check_vars.py` skips `plugins.yml` both in its known-file list and in its vault-name scan; `tests/inventory.yml`'s shared-defaults regex and `tests/precedence.sh` skip it; `tests/check_keys.yml` accepts a `vars.yml` key whose prefix is a key in the tracked `plugins` list or a committed folder in `plugins/` (CI has no fetched folders; a typo in a plugin's own setting still passes CI, and `just preview` catches it); `.ansible-lint` excludes `.fetched/` with a written reason; `tools/settings.py` also reads `plugins.yml` when present; the render test and `tests/check_keys.yml` read the committed plugins' `defaults.yml`, `defaults/main.yml` and templates; `_lint` runs `ansible-lint plugins` (ansible-lint does not find a role reached by a templated `include_role`; tested) and its shellcheck and ruff globs take `plugins/*/files`; `_syntax` adds `tools/plugins.yml`.
- Tests: the template plugin is appended to `plugin_services` in the render test, and the generic readers (`services`, `web_services`, `enabled_service_keys`, `dump_service_keys`, `oidc_service_keys`, the Homepage tile, the Caddy site) are asserted to pick it up. The generator itself runs in `just _test` against the template and the committed plugins, into a temp dir with no network and no vault: it parses, Jinja survives, entries are sorted, a collision fails. The render test's template glob also covers committed `plugins/*/templates`, so Crafty is rendered in CI; fetched plugins are not, so `just preview` is their pre-deploy check, and the docs say so.
- `docs/writing-a-plugin.md` (one page): the file list, `defaults.yml` vs `defaults/main.yml`, the `service.yml` fields (pointing at `services.yml`'s comments), `just plugins` then `just deploy <key> --limit <host>`, the `service_facts` landmine (it sets a fact named `services`, `roles/network/tasks/main.yml:33`), "your role runs as root", and removal: `just teardown <host> -e only=<key>` first, then delete the folder and rerun `just plugins` (once the entry is gone, teardown no longer knows the service). It also says: the key is the Tinyauth client id (renaming it orphans linked accounts, `services.yml:30-33`); renaming a setting or moving a data dir is a migration to announce in the plugin's README; `no_backup` means the data is in no backup; the `login` values and what each does to the gate; the plugin README lists what the operator creates. AGENTS.md gets the fourth `include_*` exception, one line naming `plugins.yml` as the one generated file in `group_vars/all/`, and the flag exception; `ansible/README.md` gets the `git` prerequisite, the file table rows and a pointer from "Add a new service"; `teardown.yml`'s usage comment points at `just teardown`, because the raw playbook never runs the generator.

## Who declares what

The plugin author knows how the software behaves; the operator knows their own setup and people. No user name lives in a plugin.

- Plugin (`service.yml`, `defaults.yml`): `login`, `oidc` redirect paths, `oidc_secret` (the vault variable's name), `container_port`, `data`, `dump_required`, `alert_to`, default settings. `login` is security-relevant (`own` turns the gate off), and the operator cannot override it per host (`service.yml` is not a setting); to disagree, keep a local copy in `plugins/<key>/` and drop the `plugins:` entry. `just plugins` prints each plugin's `login` value on the line that already shows name, version and commit.
- Operator (`vars.yml`, `host_vars`, vault): `<key>_enabled`, `<key>_sso_enabled`, `service_users.<key>` (the names must exist in `vault_tinyauth_users`), port, subdomain and drive overrides, `<key>_alert_to` (which destination), vault values, Cloudflare ingress, Copyparty logins and folders.
- The plugin's README lists what the operator must create (vault names, a Copyparty login such as `pics`); its role asserts they exist.

## Exposure and teardown

- Behind Tinyauth is the default for a web entry on a host with Tinyauth; `login: own` (the app has its own login, or its clients cannot sign in through a web page) or a fixed `port:` with no Caddy name leaves the gate off. `login: tinyauth` makes the app a Tinyauth OIDC client; `login: tinyauth_users` also says the app lets in only the users in `service_users.<key>` itself (pics).
- Public access is a Cloudflare Tunnel entry in `cloudflared_ingress`, which goes straight to a container port and bypasses Caddy and Tinyauth. It stays by hand: it allocates a public hostname that `roles/cloudflared/tasks/check.yml` cross-checks across hosts. The plugin's README names the port (as pics does with `pics_public_port`). Teardown never touches ingress or DNS; the owner removes the line.
- Teardown loops `services`, so a plugin with `compose` and `data` in its entry gets it with no extra code: compose down, dump script, compose directory, and with `remove_data=true` the `data` and `no_backup` paths, never `keep`. `just teardown` runs the generator first so the entry exists. A plugin's role keeps everything under its compose directory, its data directories and its dump script; anything else it puts on a host (cron, systemd units) is not removed. No plugin needs a hook for that yet, so none is added.

## Plugins from git

```yaml
# group_vars/all/vars.yml
plugins:
  - {key: pics, location: "https://git.example.com/owner/pics", version: v0.3.0, auth: vault_pics_repo_token}
  - {key: crafty, location: "https://github.com/someone/simple-nas-plugins", version: v1.2.0, path: crafty}
  - {key: other, location: "https://github.com/someone/simple-nas-plugins", version: v1.2.0, path: other}
```

- The list is global, in `group_vars/all/vars.yml` (the generator runs once for every host, so a `plugins` key in `host_vars` is ignored; the docs say so), and only hosts with `<key>_enabled` deploy a plugin. A local plugin needs no entry. Every entry is an https git repo with a `version` (tag, commit or branch); anything else is cloned by the owner into `plugins/`.
- `path` (optional) is the folder inside the repo that holds the plugin, for a repo with several plugins (a monorepo). Without it the repo root is the plugin. The fetch clones each repo once (the same `location` and `version`), copies the folder to `.fetched/<key>/`, so the key in the list, not the folder name in the repo, is the role name, and rejects a `path` that leaves the repo. The pics plugin lives in the pics repo, so one token (`vault_pics_repo_token`) serves both the plugin fetch and pics's own app clone.
- `auth` (optional) names a vault variable holding an access token, the pattern of `oidc_secret`; it must be in `group_vars/all/vault.yml` (the fetch runs on the controller) and the fetch asserts it exists. It is sent as an HTTP Basic header through git's environment, never in `.git/config`, scoped with `http.<scheme>://<host[:port]>/.extraHeader` built from `location` (tested: a key without the port does not match a forge on `:8443`). The user name is `x-access-token`: GitHub already uses it, and the owner confirmed Gitea accepts it. Not verified: GitLab (its docs say any non-blank name works with a token). If a forge needs another, `location: https://alice@host/...` carries it, or an `auth_user` field is added then, not before.
- `just plugins` wipes `plugins/.fetched/`, clones each entry (`depth: 1` for a tag or branch), and prints name, version and resolved commit, so a moved branch is visible. A deploy with a git plugin needs the network; `just preview` fills the cache (`check_mode: false`) and the docs say so. `no_log` only when a token is in use, so a bad URL shows git's real error. Third-party roles run as root on the hosts; listing a plugin is the consent, and the doc says to pin a tag or commit for anything not yours.

### Credentials

`vault_github_read_token` is deleted. It is read only by `roles/github_clone` and the pics role (assert, `defaults/main.yml` comment, `docs/services.md`). `github_clone` becomes a generic git clone role taking URL, `dest`, `version` and an optional token; the fetch and the pics role both call it. pics reads a token of its own (`vault_pics_repo_token`) for its app source. Until the one-time migration (its own plan: add the new names with the old value, deploy, remove the old one; vault edited by script in memory, encrypted backup first) pics keeps `vault_github_read_token`.

## Crafty and pics move

Crafty first: a leaf with no OIDC, alert sender or ingress, so it proves the mechanism with `data`, `no_backup_in`, `scheme` and `compose_service` only. Its role moves to `ansible/plugins/crafty/` with its `service.yml` and `defaults.yml`, and every Crafty name leaves the core (`defaults-*.yml`, `services.yml`, `site.yml`, `versions.yml`, tests, docs). Then pics to `ansible/plugins/pics/`, which adds `alert_to`, `login: tinyauth_users` with `oidc`, Copyparty folders and the ingress assert; its own source clone on the remote stays in its role.

The core loses in the same commit as each move, with no alias left, or `just check` is red: the flags, ports, subdomains, data dirs, extra origins, alert default and versions in `defaults-*.yml` and `versions.yml`; the entry in `services.yml`; the block in `site.yml`; the test lines in `tests/render.yml`; `pics_public_url` (no reader) and `pics_alert_to` in tracked `vars.yml`; `pics_repo` and `pics_version` are declared in the plugin's `defaults.yml` (`pics_repo` with `undef(hint=...)`) and the owner's values stay in `vars.yml`, where the `plugins:` prefix rule lets `just check` accept them; the vault and vars examples; the sections of `docs/services.md`, `docs/auth-reference.md` and `ansible/README.md` (moved into the plugin's README; run `just _links` for dangling anchors). `host_vars` keeps the flags and settings, and the pics `copyparty_folders` lines stay (Copyparty folders are by hand).

The owner's one-time steps, in `plans/plugins-migration.md`, no fallback: copy `plugins/pics/` into the pics repo, add the `plugins:` entry with a pinned tag and the token, delete the folder here in one commit; the vault token rename (see Credentials); `just plugins` and `just preview <key> --limit <host>` on each host (the diff should only be a container recreation); deploy. Vault entries stay. The plugin tag (`plugins:` version) and `pics_version` (the app's own tag) are independent: an author bumps the first when the plugin changes, the operator the second.

## Decisions

Settled: per-plugin `auth`, the central token deleted, `alert_to` kept, no Copyparty field, `path` for monorepos, Gitea user name, the pics plugin in the pics repo, Crafty a bundled plugin in `plugins/crafty/` (tracked, so CI covers it), fetch on every `deploy`, `preview` and `teardown` (one rule, no stale `plugins.yml`; local plugins work offline), the dangling flag (`just check` rejects a flag whose prefix is neither core nor in `plugins`; a listed plugin that cannot be fetched fails the fetch), one `login` field with the values `own`, `tinyauth` and `tinyauth_users` (they name what the user sees; `oidc` is jargon, and `services.yml`'s header says which values leave the gate off), no upgrade notice (KISS: a plugin's README announces a moved data dir, and the renamed-setting check makes the common case loud).
